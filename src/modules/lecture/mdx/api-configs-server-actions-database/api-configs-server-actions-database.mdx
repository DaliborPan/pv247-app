# API routes, caching, revalidation, server actions, database

In this lesson, we'll look at Next.js again in more depth. Specifically, we'll discuss the ability to create custom API endpoints. We'll learn what route segment configs are and discuss caching and revalidation options
for the individual cache layers. We'll introduce the possibility of completely avoiding writing API routes and, thus, how to use server actions. Finally, we'll look at the options for working with the database in TypeScript.

> This lecture describes **Next.js 16 with Cache Components enabled** (`cacheComponents: true` in `next.config.ts`), which is the setup this course application uses. A lot of the caching advice you will find in older tutorials and blog posts (`unstable_cache`, `export const revalidate`, `export const dynamic`, "route handlers are cached by default") describes the previous model and is either legacy or does not work at all under Cache Components. We will point out these differences as we go.

## API routes

In addition to the defined files named `page`, `loading`, `error` and so on, there is a special file named `route` which is used to define the API endpoint. Specifically, in this file, we can create a request handler that works with Web [Request](https://developer.mozilla.org/en-US/docs/Web/API/Request) and [Response](https://developer.mozilla.org/en-US/docs/Web/API/Response) objects.
We call these handlers `Route Handler`, where we can define the HTTP method the handler should handle.

We must declare these `route.ts` files inside the `app` directory, as we did with other `page` and similar files. We conventionally put these files in the `app/api/*` directory to separate our defined `api` endpoints from the classic application pages. We then call these endpoints at the URL `<domain>/api/*`.

The most common HTTP methods are `GET`, `POST`, `PUT`, `DELETE` and `PATCH`. Other supported methods are `HEAD` and `OPTIONS`. The given route handler will throw us the HTTP status `405 Method Not Allowed` for an unsupported method.

```ts
// app/api/route.ts

export const GET = () => {
  return Response.json(
    { message: 'Hello world from GET request' },
    { status: 200 }
  );
};
```

Of course, the route handler code runs on the Server where our Next.js application is running. This code is **not** executed on the Client (for example, in a browser), nor is this code sent to the Client. This is very similar to React Server Components, which are also executed on the Server, and only the result of the function is sent to the Client. In the case of the route handler, the result must be the `Response` function. It is not possible for a route handler to return nothing or to return something other than a response.

Next.js also prepared wrappers over the web Request and Response types and named them `NextRequest` and `NextResponse`, respectively, for more straightforward and more advanced usage.

In pure React, we typically apply the application architecture as Server/Client, with the Client fetching data typically via API endpoints that the Server exposes. In the case of Next.js, which allows us to retrieve data directly on the Server using the React Server Component, it is **not necessary or even correct** to call from the RSC API endpoint to retrieve data.

> If our Next.js application communicates with an external API, it is of course fine to call that API endpoint from RSC. It is wrong to call API endpoints that are defined within the same Next.js application.

```ts
// app/api/route.ts

import { getMessage } from '@/server';

export const GET = async () => {
  const text = await getMessage();

  return Response.json({ message: text }, { status: 200 });
};
```

```ts
// src/server/index.ts

import { promises as fs } from 'node:fs';

export const getMessage = async () => {
  const text = await fs.readFile('src/server/text.txt', 'utf-8');

  return text;
};
```

```tsx
// src/components/server-text.tsx

export const ServerText = async () => {
  const response = await fetch('http://localhost:3000/api');
  const json = await response.json();

  return <div>{json.message}</div>;
};
```

  This is an inappropriate way to use the GET route handler. Like the RSC code,
  the route handler code runs on the server. In this case, it is useless to call
  the actual API endpoint to execute code that will execute on the same server
  from which the endpoint is called.
</MdxComment>

```ts
// app/api/route.ts

// ❌ no need to define extra route handler
```

```ts
// src/server/index.ts
import { promises as fs } from 'node:fs';

```

```tsx
// src/components/server-text.tsx

export const ServerText = async () => {

```

  Instead of calling the route handler to execute code that must run on the

  directly in the RSC. The route handler would only be necessary if we needed to
  call this code from the client component.
</MdxComment>

### Submitting data via API routes

Until recently, the only way to create, edit or delete data in a database or other data source was by using the HTTP methods `POST`, `PUT`, `DELETE` and `PATCH` that we defined in the route handler. In the case of creating new data, we typically need to get individual information from the Client about the entity we want to create later. This code cannot run on the Server since the user enters this data through the Client, for example, a form in a browser.

```ts
// app/api/event/route.ts

export const POST = async (request: Request) => {
  const body = await request.json();

  try {
    const data = createEventSchema.parse(body);
    const event = await database.event.create(data);

    return Response.json(
      {
        message: 'Event created successfully',
        data: event
      },
      { status: 201 }
    );
  } catch (e) {
    return Response.json({ message: 'Something went wrong' }, { status: 500 });
  }
};
```

<MdxComment>
  This is what a POST route handler might look like, which creates a new `event`
  based on the data that came in the request. Just as we validated the data from
  the backend to the client using `zod`, we need to validate the data from the
  client to the server. The `createEventSchema` takes care of this, which
  defines the valid shape of the object we expect from the client. We can then
  directly access the database and thus create a new event.
</MdxComment>

### Route resolution

For route handlers, the same rules apply as far as the directory structure is concerned. If we want to create a route handler on the url `POST /api/events`, we need to create a `route.ts` file in the `app/api/events` directory and create a route handler `POST` in it.

#### Dynamic route segment

To create a dynamic route segment, i.e., a route handler that can take a dynamic `slug` in a URL, the same convention applies to creating dynamic pages.

```ts
// app/api/event/[slug]/route.ts

export const GET = async (
  _request: Request,
  { params }: RouteContext<'/api/event/[slug]'>
) => {
  const { slug } = await params;

  return Response.json({
    message: `Called with slug ${slug}`
  });
};
```

### Route handlers caching

You will often read that Next.js caches `GET` route handlers by default, so that the handler runs once during the build and the very same response is served afterwards. **This is no longer true.** Since Next.js v15, route handlers are _not_ cached by default - the handler runs on every request unless you explicitly opt into caching.

With **Cache Components** enabled, `GET` route handlers follow the same model as pages: Next.js tries to prerender them at build time and stops as soon as the handler does something that can only happen at request time. That includes reading the request object, calling `cookies()` or `headers()`, querying a database, calling an external API, or using a non-deterministic value such as `Math.random()` or `new Date()`. Other HTTP methods (`POST`, `PUT`, `PATCH`, `DELETE`) are never prerendered.

```ts
// app/api/route.ts

export const GET = () => {
  return Response.json({ projectName: 'Next.js' });
};

// Nothing here depends on the request, so this response is prerendered at build time.
```

```ts
// app/api/time/route.ts

export const GET = () => {
  return Response.json({
    time: new Date().toISOString()
  });
};

// `new Date()` is non-deterministic, so prerendering stops here
// and the handler is executed on every request.
```

If we do need data from a database or an external API in a prerendered response, we can cache that data with the `'use cache'` directive, which we will cover in detail in the caching section.

```ts
// app/api/lectures/route.ts

import { cacheLife } from 'next/cache';

const getLectures = async () => {
  'use cache';
  cacheLife('hours');

  return db.query.lectures.findMany();
};

export const GET = async () => {
  return Response.json(await getLectures());
};
```

<MdxComment>
  `'use cache'` cannot be written directly in the body of a route handler; it
  has to live in a separate `async` function that the handler calls. The cached
  result is then part of the prerendered response and is refreshed according to
  its `cacheLife` profile.
</MdxComment>

### Cookies and headers

The `cookies` and `headers` functions are so-called **request-time APIs**. They can be called from route handlers or RSCs and, relatively logically, are only available when the application is handling a request, and their result varies based on what the request looks like. Therefore, code that reads them cannot be prerendered and is executed every time the endpoint is called.

Since Next.js v15, both functions are **asynchronous** and must be awaited. Awaiting them is precisely the signal that tells Next.js this code depends on the incoming request and cannot be prerendered.

```ts
import { cookies } from 'next/headers';

export const GET = async () => {
  const cookieStore = await cookies();
  const theme = cookieStore.get('theme');

  return Response.json({
    theme: theme?.value,
    time: new Date().toISOString()
  });
};

// This route handler will run every time the endpoint is called.
```

```ts
import { headers } from 'next/headers';

export const GET = async () => {
  const headersList = await headers();
  const referer = headersList.get('referer');

  return Response.json(
    { message: 'Hello from the API' },
    { headers: { referer: referer ?? '' } }
  );
};
```

### URL query parameters

In some cases, it is appropriate to use URL query search parameters. This is the case, for example, when we want to explicitly insert a parameter into the URL that will affect the result of the route handler.

```ts
// app/api/route.ts

import { type NextRequest } from 'next/server';

export const GET = (request: NextRequest) => {
  const searchParams = request.nextUrl.searchParams;
  const color = searchParams.get('color');

  return Response.json({
    message: `Called with color: ${color}`
  });
};

// http://localhost:3000/api?color=black
```

<MdxComment>
  In this case, we add the `color` parameter to the URL query search, which will
  affect the route handler's result. Again, reading the request URL is
  request-time data, so this route handler cannot be prerendered and will be
  executed every time the endpoint is called.
</MdxComment>

## Route segment config

Route segment options configure the behavior of a `page`, `layout` or `route` by exporting a specially named variable from the file. With Cache Components enabled — which is the case in this course application — the list is much shorter than what older tutorials show.

```ts
// ✅ still available in Next.js 16

export const runtime = 'nodejs'; // the default; 'edge' is deprecated
export const maxDuration = 5; // max execution time, enforced by the platform
export const preferredRegion = 'auto'; // deprecated

// ❌ removed when `cacheComponents` is enabled

export const dynamic = 'force-dynamic'; // forced a whole route static or per-request
export const revalidate = 3600; // how often a static route was regenerated
export const fetchCache = 'only-cache'; // overrode the cache option of every fetch
export const dynamicParams = false; // 404 for params outside generateStaticParams
export const experimental_ppr = true; // PPR is not experimental anymore
```

Everything in the second group operates on a whole route at once, which is exactly what Cache Components does away with: caching is now decided **per component and per function** with `'use cache'`, and everything else either streams behind a `<Suspense>` boundary or is plain static output. The options still work in projects that have not opted into Cache Components.

Next.js 16 also adds the `prefetch` and `instant` options, which fine-tune how a route is prefetched and how instantly it can be navigated to.

### Incremental Static Regeneration

The idea behind `revalidate` has not disappeared, only the API has. A page that lists all users, for example, does not have to hit the database on every request: new users are added rarely, so the list can be generated once and regenerated periodically or on demand. Serving a prebuilt page and refreshing it in the background is called **Incremental Static Regeneration (ISR)**, and it has been in Next.js since version 12.

Under Cache Components we express the same thing with `'use cache'` plus `cacheLife` (time-based) and `cacheTag` + `revalidateTag` (on-demand). We will get to both in the caching section.

## fetch

Next.js extends the capabilities of the native web `fetch` function so that caching can be controlled directly at the request level, instead of at the level of a whole page.

### options.cache

The `cache` option is not a new property added by the Next.js team - it is available in the native `fetch` web function, Next.js only gives it an additional meaning on the server. Two settings are relevant for us:

- `force-cache` - the response is stored in the Next.js server-side cache and reused by later requests with the same URL, method, headers and body.

- `no-store` - the response is never cached and the endpoint is called on every single request.

**`fetch` is not cached by default.** This is the most common outdated claim about Next.js: in versions 13 and 14, `fetch` was cached by default and you had to opt out. Since Next.js v15, caching is **opt-in** - the default (`auto no cache`) fetches the resource on every request, and only prerendering can make it run once at build time.

```ts
export default async function Page() {
  const cachedData = await fetch('https://api.example.com', {
    cache: 'force-cache'
  });

  const freshData = await fetch('https://api.example.com', {
    cache: 'no-store'
  });

  return (
    ...
  );
}

```

### options.next

Next.js adds the `next` option, which carries two further options, namely `revalidate` and `tags`. The `revalidate` option sets the cache lifetime of that single request in seconds.

The `tags` option allows us to assign an identifier to a request, so that it can later be revalidated on demand with `revalidateTag`.

```ts
export default async function Page() {
  const response = await fetch('https://api.example.com', {
    next: { revalidate: 3600, tags: ['api', 'example'] }
  });

  return (
    ...
  );
}

```

<MdxComment>
  These `fetch`-level options still work, but they only ever covered `fetch`.
  With Cache Components, the recommended way to cache anything - a `fetch`, a
  database query, an expensive computation or a whole component - is the `'use
  cache'` directive described below.
</MdxComment>

## Server actions

Server actions are a way to call a function from the client that will run on the server, without having to create a route handler for it. We can even create forms this way, where we use server actions to send all the data that the user fills in to the server, where the server function is run and then the result is returned to the client.

In React terminology, an asynchronous function marked with `'use server'` is a **server function**; a server function invoked through React's action mechanisms (`<form action>`, `<button formAction>`, or a client-side transition) is a **server action**. The two terms are often used interchangeably.

### Differentiation from the traditional endpoint API

Using server actions is quite different from the traditional way of calling the classic POST/PUT/DELETE API endpoint in the `onSubmit` event handler of the `<form>` tag.

#### API POST route handler

Let's take an example of a POST API endpoint to create a new event. The user fills out a form on the client and clicks a button that invokes this POST API endpoint. Code is executed inside the route handler, a new event is created, and the newly created object is typically returned in the response. However, now the user needs to provide new data where all events are shown, for example. Therefore, the client (browser) has to send another request to the server to get the updated list of events, where in the response this list is returned to the client and can be rendered on the screen.

#### POST server action

The beginning is practically the same - the user fills in the form and clicks the button to create a new event. This triggers a POST request to the server again, sending the data that the user has filled in. This request, however, executes the server action we defined. The code to add the new event is executed, and because we are in a server action, it is possible to call a special function to revalidate either the entire page or just an endpoint. This allows the page to be re-rendered and prepared on the server with the new data already in it - the new event list, including the newly added and reverted original POST request, returns a response that already contains the new UI for the client, which just displays it on the screen. No need to perform another extra request to the server to get the new data.

### Get started - forms

When using a server action from a form, we use the `action` prop, which is defined on the `<form>` tag. As `action`, we pass a function that takes the `FormData` of the form that is being submitted as its parameter. This `action` can either be in a separate file, or defined within the same component where the form resides. The function must be marked as `'use server'`.

```tsx
// src/app/server-action/page.tsx

import { addTodoAction } from '@/server-actions';
import { readTodos } from '@/server';
import { SubmitFormButton } from './submit-form-button';

export default async function Page() {
  const data = await readTodos();

  return (
    <div>
      <h1>Home</h1>
      <ul>
        {data.map(todo => (
          <li key={todo.id}>{todo.title}</li>
        ))}
      </ul>
      <form action={addTodoAction}>
        <SubmitFormButton />
      </form>
    </div>
  );
}
```

```ts
// src/server-actions/index.ts

'use server';

import { revalidatePath } from 'next/cache';
import { addTodo } from '../server';

export const addTodoAction = async () => {
  await addTodo();

  revalidatePath('/server-action');
};
```

```tsx
// src/app/server-action/submit-form-button.tsx

'use client';

import { useFormStatus } from 'react-dom';

export const SubmitFormButton = () => {
  const formStatus = useFormStatus();

  return (
    <button type="submit">
      {formStatus.pending ? 'Adding todo...' : 'Add todo'}
    </button>
  );
};
```

<MdxComment>
  In this case we have the server action extracted into its own file, which is
  marked as `use server`, which means that this code will safely run only on the
  server and not even sent to the client. `useFormStatus` reports whether the
  surrounding form is being submitted and has to be called from a component that
  is **inside** the `<form>` — that is why `SubmitFormButton` is a separate
  client component.
</MdxComment>

```tsx
import { revalidatePath } from 'next/cache';
import { addTodo, readTodos } from '@/server';
import { SubmitFormButton } from './submit-form-button';

export default async function Page() {
  const data = await readTodos();

  const addTodoAction = async () => {
    'use server';

    await addTodo();
    revalidatePath('/server-action');
  };

  return (
    <div>
      <h1>Home</h1>
      <ul>
        {data.map(todo => (
          <li key={todo.id}>{todo.title}</li>
        ))}
      </ul>
      <form action={addTodoAction}>
        <SubmitFormButton />
      </form>
    </div>
  );
}
```

<MdxComment>
  In this case, we have a server action defined directly within the component
  where the form that invokes the action occurs.
</MdxComment>

### Security

A server action is compiled into a **public HTTP endpoint**. The `'use server'` directive replaces the function body in the client bundle with a reference (an action ID) that performs a `POST` request back to the server. Anyone who can send that `POST` request can invoke the action - they do not have to go through your UI at all.

Next.js provides a few framework-level protections: it compares the request `Origin` against the `Host` (a CSRF check), limits the request body to 1 MB by default, encrypts action IDs and closed-over variables, and removes unused server functions from the client bundle. **None of this replaces your own checks.** Inside every single server action you must:

- **Authenticate and authorize.** The fact that the form is only rendered on a page behind a login is not a security boundary.
- **Validate the input.** Treat `FormData`, parameters and headers as untrusted data and parse them with `zod` or a similar library.
- **Only accept what the client is allowed to decide.** Send an ID plus the change, and re-read everything else (ownership in particular) from a trusted source using the session. Schema validation only checks the _shape_ of the input - a perfectly valid object can still refer to a row that the caller does not own.
- **Constrain the return value.** What an action returns is serialized to the client, so return what the UI needs, not raw database rows.

```ts
'use server';

import { auth } from '@/auth';
import { db } from '@/db';

export const deleteTodoAction = async (todoId: string) => {
  const session = await auth();

  if (!session?.user) {
    throw new Error('Unauthorized');
  }

  // the todo is looked up by its id AND its owner
  const todo = await db.query.todos.findFirst({
    where: and(eq(todos.id, todoId), eq(todos.ownerId, session.user.id))
  });

  if (!todo) {
    throw new Error('Forbidden');
  }

  await db.delete(todos).where(eq(todos.id, todo.id));
};
```

### Type safety

One of the drawbacks of plain server actions is that the `formData` sent to them is not typed, and we have to validate it ourselves, typically with `zod`. Libraries such as [next-safe-action](https://next-safe-action.dev) go one step further and wrap an action into a typed procedure: the input is described by a schema and validated automatically, and authentication can be factored out into a reusable procedure that every action builds on — the "authorize on every action" rule from the previous section, enforced by construction.

## Revalidation

Notice that the server action above does not only add a `todo` - it also calls `revalidatePath`. Without that call the page would keep showing the old list. The component that reads the todos is a server component, and nothing re-renders it just because we changed a row in the database.

### One request, two things in the response

This is what makes a server action fundamentally different from a POST endpoint. When an action invalidates something, Next.js runs the action **and** re-renders the current route within the same HTTP request. The response then carries two things at once:

- the value the action returned, which is what `useActionState` or the awaited call receives on the client, and
- a freshly rendered RSC payload of the current route, which the router commits immediately.

The browser therefore never has to ask for the new UI in a second request.

The re-render is included in the response whenever the action

- calls `updateTag` or `revalidatePath` to invalidate cached data immediately,
- calls `refresh` to refetch the RSC payload of the current route,
- sets or deletes a cookie through `cookies()`, or
- calls `redirect` - in which case the response navigates the router and streams the destination route instead.

`revalidateTag` is the exception: it marks the tag for a background refresh, so the action's own response does **not** wait for the new data and the change shows up on a later read.

<MdxComment>
  `redirect` works by throwing a control-flow exception, so no code after it in
  the action is executed. Put the revalidation call **before** the `redirect` if
  the destination page needs the fresh data.
</MdxComment>

### Choosing how to update the cache

All four functions come from `next/cache` and all of them are called at the end of a mutation, but they do different things:

- `updateTag(tag)` - expires the tag immediately. The re-render that ships with the action's response already waits for the fresh data, so the user sees their own change. This is what you want after a mutation the user just triggered. **Server actions only.**

- `revalidateTag(tag, 'max')` - stale-while-revalidate. Later reads get the stale value while a fresh one is computed in the background. Allowed in route handlers as well, which is what a CMS webhook would use.

- `revalidatePath(path)` - invalidates everything cached for one route. Useful when a single page is affected and tagging would be overkill, but it is the bluntest of the four.

- `refresh()` - only refetches the RSC payload of the current route, without invalidating any cache entry. Reach for it when the action changed something that is not in the cache at all, typically a value stored in cookies. **Server actions only.**

<MdxComment>
  Prefer the tag-based functions. A tag describes the **data**, so one call
  covers every page that displays it, while `revalidatePath` has to be repeated
  for every affected URL and throws away everything cached on that route.
</MdxComment>

### Server action vs POST request

So we now have two ways of creating, updating and deleting data from the client. The two differences worth remembering:

**Need for JavaScript**

- A server action passed to `<form action={...}>` is submitted by the browser itself. The form therefore works before the page is hydrated and keeps working for a user whose JavaScript failed to load - a property called progressive enhancement.

- A traditional POST endpoint is always invoked from JavaScript: something has to collect the values, build the request and send it to the right URL.

**Getting the new UI**

- With a server action, the mutation, the cache invalidation and the re-render of the page happen in a single roundtrip, as described above.

- With a POST endpoint, the request only creates the entity. To display the new list we need a second request: `router.refresh()` when the list is rendered by a server component, or `queryClient.invalidateQueries` when the list is fetched on the client with TanStack Query.

> Both approaches are valid and you will meet both. A reasonable rule of thumb: if the data on the screen is rendered by a server component, use a server action; if the mutation is part of a client-side data flow that TanStack Query already manages, an endpoint fits in more naturally.

## Server actions called from a client component

So far we have passed the action to `<form action={...}>`. A server action is an ordinary async function, though, so a client component can import it and call it directly - from an `onSubmit` handler, from a button's `onClick`, or from the `handleSubmit` of React Hook Form. We keep all the benefits (no extra route handler, typed arguments, revalidation on the server) and can use the form library we already know.

What we lose is the automatic pending state: outside a `<form action={...}>` there is nothing for `useFormStatus` to report on. The replacement is `useTransition`, which gives us the same `pending` flag and lets React keep the rest of the UI interactive while the action runs. (With React Hook Form we do not need it - `formState.isSubmitting` already tracks the promise returned from `handleSubmit`.)

```tsx
// src/app/server-action/page.tsx

import { readTodos } from '@/server';

import { AddTodoForm } from './add-todo-form';

export default async function Page() {
  const data = await readTodos();

  return (
    <div>
      <h1>Home</h1>
      <ul>
        {data.map(todo => (
          <li key={todo.id}>{todo.title}</li>
        ))}
      </ul>
      <AddTodoForm />
    </div>
  );
}
```

```tsx
// src/app/server-action/add-todo-form.tsx

'use client';

import { type FormEvent, useState, useTransition } from 'react';

import { addTodoAction } from './actions';

export const AddTodoForm = () => {
  const [title, setTitle] = useState('');
  const [isPending, startTransition] = useTransition();

  const onSubmit = (event: FormEvent<HTMLFormElement>) => {
    event.preventDefault();

    startTransition(async () => {
      await addTodoAction({ title });
      setTitle('');
    });
  };

  return (
    <form onSubmit={onSubmit}>
      <input
        onChange={e => setTitle(e.target.value)}
        type="text"
        value={title}
      />
      <button disabled={isPending} type="submit">
        {isPending ? 'Adding todo...' : 'Add todo'}
      </button>
    </form>
  );
};
```

```ts
// src/app/server-action/actions.ts

'use server';

import { revalidatePath } from 'next/cache';
import { z } from 'zod';

import { addTodo } from '@/server';

const addTodoSchema = z.object({
  title: z.string().min(1)
});

export const addTodoAction = async (input: unknown) => {
  // the client is not a trusted source, so the input is parsed here as well
  const { title } = addTodoSchema.parse(input);

  await addTodo(title);

  revalidatePath('/server-action');
};
```

<MdxComment>
  Note that the action takes `unknown` and parses it. The type of the argument
  is only a compile-time promise; the action is a public endpoint, and anyone
  can `POST` anything to it. This is the "validate the input" rule from the
  security section, applied to an action that is called from our own form.
</MdxComment>

The [next-safe-action](https://next-safe-action.dev/docs/getting-started) library mentioned earlier removes most of this boilerplate: it takes the schema, validates the input for us and hands the action a typed value.

For a broader walkthrough of what server actions can do, we recommend [this video](https://www.youtube.com/watch?v=cY2SpxhEdyE).

## Caching

Caching used to be the hardest part of Next.js to learn. In versions 13 and 14 a lot of it was on by default and the skill was knowing how to opt **out**. Since v15 the defaults are the opposite - nothing is cached unless you ask for it - and Next.js 16 with Cache Components reduces the whole topic to one explicit tool: the `'use cache'` directive, plus two functions that describe how long an entry lives and how it is invalidated.

> Most caching is invisible in development. It only shows up when the application runs in production mode (`next build && next start`), which is what makes it hard to debug. Never draw conclusions about caching from `next dev` alone.

### The layers

It still helps to know what sits where, because the four layers are invalidated differently:

- **Request memoization** - within a single render pass, `GET` `fetch` calls with the same URL and options are executed once and the result is shared. This is not a cache that survives the request; it only means that a `Parent` and a nested `Child` asking for the same data do not produce two requests. For anything that is not `fetch`, such as a database query, React's `cache()` function does the same job. Memoization does not apply in route handlers, since they are not part of the React component tree.

- **`'use cache'`** - the actual cache. It stores the output of a function or a component, it is shared across requests and across users, and its lifetime is described by `cacheLife`. This is the layer we control.

- **The prerendered output** - the HTML and the RSC payload produced at build time, in other words the static shell from the previous lecture. Everything static, plus every `'use cache'` result whose lifetime is long enough, ends up here and can be served from a CDN.

- **The client router cache** - the browser keeps the RSC payloads it has already received, from a navigation or from a prefetch, and reuses them while they are fresh. How long that is comes from the `stale` value of the cache profile, with a minimum of 30 seconds enforced by the router.

<MdxComment>
  All of these are scoped to a single deployment. A new deploy starts with empty
  caches, because the build id is part of every cache key. Also note that by
  default the server-side store is in memory, so on a serverless platform (such
  as Vercel) an entry does not necessarily survive from one request to the next.
</MdxComment>

### The `'use cache'` directive

`'use cache'` marks an async function, component, page or layout as cacheable. It can be placed as the first statement of a function body, or at the top of a file, in which case every export of that file is cached and all of them have to be `async`.

```ts
// src/server/todos.ts

import { cacheLife, cacheTag } from 'next/cache';

import { db } from '@/db';

export const readTodos = async () => {
  'use cache';
  cacheTag('todos');
  cacheLife('hours');

  return db.query.todos.findMany();
};
```

The cache key is built from the arguments of the function **and** from every value it closes over, so `readTodos(userId)` produces a separate entry for each user. This is also why the arguments and the return value have to be serializable - a class instance or a function cannot be part of a cache entry.

There are two ways of using the directive and both are common:

- **data-level** caching, as above: a function that reads data is cached, and any component may call it.
- **UI-level** caching: `'use cache'` at the top of a component, page or layout, so the rendered output is cached, not just the data.

<MdxComment>
  A cached function must not read request data. Calling `cookies()`, `headers()`
  or awaiting `searchParams` inside a `'use cache'` scope is an error - and so
  is calling a helper that does it. Read the value outside the cached scope and
  pass it in as an argument; it then becomes part of the cache key.
</MdxComment>

### cacheLife

`cacheLife` sets how long an entry is usable. It takes the name of a profile, or an object for full control. The built-in profiles are:

- `seconds` - refreshed after 1 second, expires after a minute
- `minutes` - refreshed after a minute, expires after an hour
- `hours` - refreshed after an hour, expires after a day
- `days` - refreshed after a day, expires after a week
- `weeks` - refreshed after a week, expires after 30 days
- `max` - refreshed after 30 days, expires after a year
- `default` - what applies when you do not call `cacheLife` at all: refreshed after 15 minutes, never expires

Each profile actually carries three values - `stale` (how long the **browser** reuses it), `revalidate` (after how long the **server** recomputes it) and `expire` (when the entry may no longer be served at all) - and you can set them directly in seconds:

```ts
'use cache';
cacheLife({ stale: 3600, revalidate: 7200, expire: 86400 });
```

<MdxComment>
  Always write an explicit `cacheLife`; it makes the behaviour visible at the
  call site. Note that a very short lifetime (the `seconds` profile) is
  deliberately excluded from prerendering - such an entry would be stale before
  anyone could read it, so it becomes a dynamic hole in the shell instead.
</MdxComment>

### cacheTag and on-demand invalidation

Time-based expiry is not enough for data that changes when a user does something. `cacheTag` labels the entry, and a server action then invalidates every entry with that label using the functions from the [revalidation](#revalidation) section:

```ts
// src/app/server-action/actions.ts

'use server';

import { updateTag } from 'next/cache';

import { addTodo } from '@/server';

export const addTodoAction = async (title: string) => {
  await addTodo(title);

  // every 'use cache' entry tagged 'todos' is expired,
  // and the page re-rendered in this same response reads fresh data
  updateTag('todos');
};
```

This pairing - a long `cacheLife` plus a `cacheTag` invalidated on demand - is the recommended default for data that only changes when someone edits it. It is exactly what this course application does with the list of lectures: it is cached with the `max` profile and tagged, and publishing a lecture invalidates the tag, without rebuilding the application.

### Request memoization

Finally, a short demonstration of the layer we cannot turn off. The same `fetchData` function is called by two components in the same tree:

```tsx
import { Suspense } from 'react';
import { z } from 'zod';

const url = 'https://api-example.com/users';

async function fetchData() {
  const response = await fetch(url);
  const data = z
    .array(z.object({ id: z.string() }))
    .parse(await response.json());

  return data;
}

async function Child() {
  const data = await fetchData();
  const first = data[0];

  if (!first) {
    return null;
  }

  return (
    <div>
      <h1>This is first ID: {first.id}</h1>
    </div>
  );
}

async function Parent() {
  const data = await fetchData();

  return (
    <div>
      <div className="flex gap-x-2">
        {data.slice(0, 2).map(user => (
          <div key={user.id}>{user.id}</div>
        ))}
      </div>
      <Suspense fallback={<div>Child loading...</div>}>
        <Child />
      </Suspense>
    </div>
  );
}

export default function Page() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <Parent />
    </Suspense>
  );
}
```

<MdxComment>
  The `fetch` is executed only once, in the `Parent` component. The page first
  shows the `Loading...` fallback defined in `Page`. Once `Parent` has the data
  it starts rendering, reaches the asynchronous `Child` and renders the `Child
  loading...` fallback - but that one is barely visible, because `Child` calls
  the very same `fetch` and gets the memoized result immediately.
</MdxComment>

Two rules to keep in mind:

- Memoization applies to `fetch` with the `GET` method and only within one render pass. It is not a cache: the next request starts from scratch.

- It only works inside the React component tree, so a `fetch` called in a route handler is not memoized. If we talk to the database directly instead of using `fetch`, React's `cache()` function does the same deduplication for our own function.

### The previous model, for context

You will find a lot of blog posts, tutorials and even AI answers describing Next.js caching as four separate mechanisms: Request Memoization, Data Cache, Full Route Cache and Router Cache.

<MdxImage
  src={CACHE_DIAGRAM}
  alt="Diagram of the four caching layers of the previous Next.js model"
/>

That model is what Next.js 13 and 14 did, and the reason it had such a bad reputation is visible in the diagram: four layers with different lifetimes, different invalidation rules and mostly enabled by default. Cache Components replaces the two middle layers with the single `'use cache'` directive that you place where the data actually is. If you ever work on a project that has not opted into Cache Components, Next.js keeps the old behaviour documented in the [Caching and Revalidating (Previous Model)](https://nextjs.org/docs/app/guides/caching-without-cache-components) guide.

## Database

The server part of a Next.js application runs in a full Node.js environment, so it can act as a complete backend - and one of the things a backend usually takes care of is database access. As with everything else in JavaScript there are several options to choose from, and most of them can infer types from your tables, so you write type-safe queries instead of raw SQL.

### Drizzle

Drizzle is an Object-Relational Mapping (ORM) library designed for TypeScript and for environments like Next.js. An ORM maps database tables to objects in code, which makes database operations more readable and reduces the amount of SQL that has to be written and maintained by hand.

The best known alternative is Prisma. We have picked Drizzle for this course because its schema is written in plain TypeScript - there is no separate schema language to learn and no code generation step, and the query builder stays close to the SQL it produces.

For the database itself we use `Turso`, a provider with a free tier and good support for Drizzle. We recommend it for your final project as well.

```bash
npm i drizzle-orm @libsql/client
npm i -D drizzle-kit
```

Turso is built on SQLite, which is more than enough for the applications we build in this course. Should you ever need a different database, Drizzle supports PostgreSQL and MySQL as well - the schema and the queries stay in the same style, you only import the column types from a different module.

To work with the database we first need to define our tables (models, schemas). We create them in `src/db/schema/*`, one file per model.

```ts
// src/db/schema/todos.ts

import { sqliteTable, text } from 'drizzle-orm/sqlite-core';

export const todos = sqliteTable('todos', {
  id: text('id')
    .primaryKey()
    .$defaultFn(() => crypto.randomUUID()),
  title: text('title').notNull()
});
```

<MdxComment>
  For all the column types supported in SQLite, see the [drizzle
  documentation](https://orm.drizzle.team/docs/column-types/sqlite).
</MdxComment>

Then we need one database instance that the whole application shares, typically in `src/db/index.ts`. Note that we pass the schema to `drizzle` - that is what gives us the fully typed `db.query` API.

```ts
// src/db/index.ts

import { drizzle } from 'drizzle-orm/libsql';

import { todos } from './schema/todos';

export const db = drizzle({
  connection: {
    url: process.env.DATABASE_URL!,
    authToken: process.env.AUTH_TOKEN
  },
  schema: { todos }
});
```

<MdxComment>
  With the schema passed in, we can write `db.query.todos.findMany()` - the
  relational API, which returns typed rows and can load relations with `with`.
  Without it, only the SQL-like builder (`db.select().from(todos)`) is
  available. You can find exactly this setup in `src/db/index.ts` of this course
  application.
</MdxComment>

<MdxComment>
  In this way we create tables that we will then use within our application. For
  more information about all the possible data types supported in SQlite, we
  recommend [drizzle
  documentation](https://orm.drizzle.team/docs/column-types/sqlite).
</MdxComment>

### Turso

Turso offers a free tier, which is all we need for the homework and for the final project. After creating an account, install their CLI and create a database:

```bash
turso db create pv247-app
turso db show pv247-app --url
turso db tokens create pv247-app -e none
```

The URL and the token are the two values our client needs, so we store them in `.env` as **DATABASE_URL** and **AUTH_TOKEN** - the names we read in `src/db/index.ts` above. See the [Turso documentation](https://docs.turso.tech/quickstart) for the full setup.

#### Local development

We do not have to talk to the deployed database while developing. Because Turso is built on SQLite, the CLI can run a local database for us, and switching to the real one is a matter of changing `DATABASE_URL`.

- Start the local database with `turso dev --db-file dev.db`. Without `--db-file` the data lives only in memory and is lost when you stop the server.

- Set `DATABASE_URL` to `http://127.0.0.1:8080`, the address the local server uses by default. The local server needs no token, so `AUTH_TOKEN` stays empty.

#### Migrations

The tables described in `src/db/schema` do not exist in the database until we apply them. That is the job of `drizzle-kit`, which needs a `drizzle.config.ts` file in the root of the project (next to `package.json`).

```ts
// drizzle.config.ts

import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema: ['./src/db/schema/*'],
  out: '.drizzle',
  dialect: 'turso',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
    authToken: process.env.AUTH_TOKEN
  }
});
```

<MdxComment>
  Older tutorials pass a `driver` option instead of `dialect`, which current
  versions of `drizzle-kit` no longer accept. The config above is the one this
  course application uses.
</MdxComment>

There are two ways of getting the schema into the database:

```bash
# applies the current schema directly, without creating migration files
npx drizzle-kit push

# or: generate a migration file and apply it afterwards
npx drizzle-kit generate
npx drizzle-kit migrate
```

`push` is the fast path and it is what we use during the semester: it compares the schema with the database and applies the difference. For a real project you eventually want `generate` + `migrate`, because the migration files are versioned in git and give you a reproducible history of the schema.

Either way, the command has to be run again after every schema change, otherwise the database will not match the TypeScript definitions - and Drizzle will happily let you write a query against a column that does not exist in the database yet.

## Complete example - server actions, database, caching

We now have everything needed for a small CRUD application. The example below puts the three topics of this lesson together: the list is read by a server component through a cached function, the form is a client component built with React Hook Form, and the mutation is a server action that validates its input and invalidates the cache tag.

```ts
// src/server/todos.ts

import { cacheLife, cacheTag } from 'next/cache';

import { db } from '@/db';
import { todos } from '@/db/schema/todos';

export const readTodos = async () => {
  'use cache';
  cacheTag('todos');
  cacheLife('max');

  return db.query.todos.findMany();
};

export const createTodo = async (title: string) => {
  await db.insert(todos).values({ title });
};
```

```tsx
// src/app/todos/page.tsx

import { readTodos } from '@/server/todos';

import { AddTodoForm } from './add-todo-form';

export default async function Page() {
  const data = await readTodos();

  return (
    <div>
      <ul>
        {data.map(todo => (
          <li key={todo.id}>{todo.title}</li>
        ))}
      </ul>

      <AddTodoForm />
    </div>
  );
}
```

```ts
// src/app/todos/schema.ts

import { z } from 'zod';

export const todoFormSchema = z.object({
  title: z.string().min(1, 'Title is required')
});

export type TodoFormSchema = z.infer<typeof todoFormSchema>;
```

```tsx
// src/app/todos/add-todo-form.tsx

'use client';

import { zodResolver } from '@hookform/resolvers/zod';
import { useForm } from 'react-hook-form';

import { addTodoAction } from './actions';
import { type TodoFormSchema, todoFormSchema } from './schema';

export const AddTodoForm = () => {
  const form = useForm<TodoFormSchema>({
    resolver: zodResolver(todoFormSchema),
    defaultValues: { title: '' }
  });

  const onSubmit = async (values: TodoFormSchema) => {
    await addTodoAction(values);
    form.reset();
  };

  return (
    <form onSubmit={form.handleSubmit(onSubmit)}>
      <input {...form.register('title')} type="text" />
      {form.formState.errors.title && (
        <p>{form.formState.errors.title.message}</p>
      )}

      <button disabled={form.formState.isSubmitting} type="submit">
        Submit
      </button>
    </form>
  );
};
```

```ts
// src/app/todos/actions.ts

'use server';

import { updateTag } from 'next/cache';

import { createTodo } from '@/server/todos';

import { todoFormSchema } from './schema';

export const addTodoAction = async (input: unknown) => {
  const { title } = todoFormSchema.parse(input);

  await createTodo(title);

  updateTag('todos');
};
```

<MdxComment>
  The schema lives in its own file for a reason: a file marked `'use server'`
  may only export async functions, so the schema and its type cannot be exported
  from `actions.ts`. Both the form and the action then import the same schema,
  which is what keeps the client-side and the server-side validation in sync.
</MdxComment>

Follow what happens after the button is clicked. React Hook Form validates the input on the client and calls the action. The action parses the input again - it is a public endpoint, so the client is not a source we can trust - writes the row and expires the `todos` tag. Because `updateTag` runs inside a server action, Next.js re-renders the page within the same response, `readTodos` misses the cache and reads the new row, and the browser gets the updated list without ever sending a second request.
