# Authentication, metadata, deployment and Turbo

In the last lesson of this course, we will focus on an important part of most web applications, which is user authentication. Next, we'll look at metadata and how it can be set up and used in our applications. We'll look at deployment options for our applications, specifically one of the easiest options, which is deploying to the Vercel platform. We'll briefly mention tools like Turbopack and Turborepo that can be useful for larger projects.

## Authentication

Many web applications allow the user to log in and continue with the application where authentication is required. As a developer, we need to address access to our application so that those parts of the application where authentication is required are only available to logged in users.

There are many ways we can authenticate users. From simple login using a name and password (or just a password), to logging in using social networks, to authentication using biometrics. In this lesson, we'll demonstrate authentication via GitHub, but the principles are the same for all other authentication methods. We will use the `better-auth` library to easily add authentication to our application. It is generally not a good idea to implement your own authentication system, but rather use a well-tested library.

We will store the logged in users in a database, similar to the last lesson. Therefore, we will again use Drizzle and SQLite.

## Better Auth

For authentication management we will use [Better Auth](https://www.better-auth.com/). It is a framework-agnostic authentication library written in TypeScript that works very well with the Next.js App Router. It is also the library that this PV247 application itself is built on, so everything shown here is code you can find in the course repository.

<MdxComment>
  You will still find a lot of tutorials that use `next-auth` (or Auth.js).
  It is not the recommended approach anymore, Better Auth became the new standard.
  The main practical difference is that with Better Auth the database schema, the
  configuration and all the generated types live in your own project, so there
  is much less hidden magic.
</MdxComment>

```bash
pnpm add better-auth
```

After installation we need to set the `.env` variables. Two of them belong to the library itself:

- `BETTER_AUTH_SECRET` - a random string used to sign and encrypt cookies and tokens. You can generate one with `openssl rand -base64 32`.
- `BETTER_AUTH_URL` - the base URL of the application, `http://localhost:3000` during development.

On top of that, we add the credentials of every provider we want to use. In our case we use GitHub, so we add `AUTH_GITHUB_ID` and `AUTH_GITHUB_SECRET`.

The whole server-side configuration is a single `betterAuth` call. We create a file `src/auth/auth.ts`:

```ts
import { betterAuth } from 'better-auth';
import { drizzleAdapter } from 'better-auth/adapters/drizzle';

import { db } from '../db';
import { user, session, account, verification } from '../db/schema/users';

export const auth = betterAuth({
  database: drizzleAdapter(db, {
    provider: 'sqlite',
    schema: { user, session, account, verification }
  }),
  socialProviders: {
    github: {
      clientId: process.env.AUTH_GITHUB_ID!,
      clientSecret: process.env.AUTH_GITHUB_SECRET!
    }
  }
});
```

<MdxComment>
  The `auth` object is the server side of the library. It contains `auth.handler`
  (a plain function that takes a `Request` and returns a `Response`) and
  `auth.api`, which exposes server functions such as `getSession`. It must never
  be imported into a client component - it talks to the database and reads the
  secrets.
</MdxComment>

Better Auth serves all of its endpoints - sign in, sign out, the OAuth callback, session lookup and so on - from a single **catch-all route**. We create `src/app/api/auth/[...all]/route.ts` and hand the whole `/api/auth` subtree over to the library:

```ts
import { toNextJsHandler } from 'better-auth/next-js';

import { auth } from '@/auth/auth';

export const { GET, POST } = toNextJsHandler(auth.handler);
```

Better Auth also ships a `nextCookies` plugin, which the official Next.js setup
recommends adding right away. It has to be the last plugin in the list:

```ts
import { nextCookies } from 'better-auth/next-js';

export const auth = betterAuth({
  // ...the rest of the configuration
  plugins: [nextCookies()]
});
```

<MdxComment>
  Why is the plugin needed? The route handler above returns a `Set-Cookie`
  header and the browser stores the session cookie on its own. A **server
  action** that calls an auth endpoint has no such response, so the cookie would
  be dropped. The plugin hooks into the response and writes the cookie through
  `next/headers` instead. The GitHub flow in this lesson works without it, but
  anything signing users in from a server action does not.
</MdxComment>

Finally we need a **client instance**, the counterpart used from client components. It does not contain any secret, it only knows how to call the endpoints above. We create `src/auth/client.ts`:

```ts
'use client';

import { createAuthClient } from 'better-auth/react';

export const authClient = createAuthClient();

export const { signIn, signOut, useSession } = authClient;
```

<MdxComment>
  We import the client from `better-auth/react`, which is the variant that also
  gives us the reactive `useSession` hook. If we do not pass a `baseURL`, the
  client uses the origin the page was served from.
</MdxComment>

We create our own `/login` page and call `signIn.social({ provider: 'github' })` from its button. After clicking the button, the browser is redirected to GitHub and then back to our application.

### Working with active session

On the server, we get the currently logged in user through `auth.api.getSession`. It needs the request headers because Better Auth reads the session cookie from them. It returns the session when the user is logged in and `null` otherwise.

```tsx
import { redirect } from 'next/navigation';
import { headers } from 'next/headers';

import { auth } from '@/auth';

export default async function Page() {
  const session = await auth.api.getSession({
    headers: await headers()
  });

  if (!session) {
    redirect('/login');
  }

  return (
    <div>
      <h1>Current user: {session.user.name}</h1>
      <pre>{JSON.stringify(session.user, null, 2)}</pre>
    </div>
  );
}
```

<MdxComment>
  In this example, we get the current session through `auth.api.getSession`.
  This code runs only on the server: it reads the request headers and talks to
  the database. If the session does not exist, we redirect to our own `/login`
  page, which contains the GitHub sign-in button.
</MdxComment>

The session contains the user with the basic information we get from the provider, including Better Auth's string `id`.

```json
{
  "id": "user-id",
  "name": "GitHub name",
  "email": "GitHub email",
  "image": "https://avatars.githubusercontent.com/u/1234567?v=4"
}
```

The `user.id` is the value we use as a foreign key in tables owned by our application. Better Auth creates the user, account and session records automatically when a user signs in for the first time.

### Drizzle adapter

The `drizzleAdapter` imported from `better-auth/adapters/drizzle` connects Better Auth to our Drizzle schema. The adapter is part of `better-auth`; no separate `@auth/*` packages are needed. It needs the four tables `user`, `session`, `account` and `verification`, which we pass explicitly in the configuration shown at the beginning of this lesson.

We do not have to write those four tables by hand. Better Auth ships a CLI that
reads our `auth.ts` and generates the schema for the adapter we configured:

```bash
npx auth@latest generate
```

For Drizzle it writes the `user`, `session`, `account` and `verification` tables
into a schema file, which we then apply to the database with Drizzle itself:

```bash
npx drizzle-kit push
```

<MdxComment>
  The CLI is published as `auth`; the older `@better-auth/cli` name is
  deprecated. Note that `npx auth@latest migrate` only works with the built-in
  Kysely adapter - with Drizzle we always apply the schema through
  `drizzle-kit`.
</MdxComment>

The tables belong in our project, so we can extend the `user` table with application-specific columns. This course application, for example, adds `role`, `firstName`, `lastName` and `github`:

```ts
// src/db/schema/users/users.ts
export const user = sqliteTable('user', {
  id: text('id').primaryKey(),
  name: text('name').notNull(),
  email: text('email').notNull().unique(),
  // ...the remaining Better Auth columns

  role: text('role').default('student').notNull(),
  firstName: text('firstName'),
  lastName: text('lastName'),
  github: text('github')
});
```

After changing the schema, apply the change to the database with the migration workflow your project uses. This repository uses `npx drizzle-kit push`. When experimenting with a disposable local database, deleting it and pushing the schema again is also fine; never do that with production data.

When a user logs in, Better Auth creates the required user, account and session rows. We can query the user row and use its `id` in our own tables without writing a session callback or augmenting library-owned TypeScript types.

## Drizzle - 1:M relationship

Since we are already able to retrieve and store the `id` of the user who is logged in, let's create a second table that will contain the user reference as a foreign key. So let's create an `event` table that will contain `user_id` as the foreign key.

```ts
import { sqliteTable, text } from 'drizzle-orm/sqlite-core';
import { user } from './users';

export const events = sqliteTable('event', {
  id: text('id')
    .notNull()
    .primaryKey()
    .$defaultFn(() => crypto.randomUUID()),
  userId: text('user_id')
    .notNull()
    .references(() => user.id),
  name: text('name')
});
```

<MdxComment>
  We use `crypto.randomUUID()` to generate a unique `id` for each new record in the `event`
  table. This is so that we don't have to manually enter the `id` each time we
  create a new record in the `event` table.
</MdxComment>

### Example implementation of creating an event for logged in user

Here is an example of how we can get information on the page about whether the user is logged in. If so, we get all the events that belong to the logged in user and list them on the screen. Next, we render a form component on the screen to add a new event. When the `Submit` button is clicked, the server action is called, which again retrieves the information about which user called this server action and creates a new event in the database. Finally, we call `revalidatePath("/protected")` to update the list of events on the screen.

```tsx
import { eq } from 'drizzle-orm';
import { redirect } from 'next/navigation';
import { headers } from 'next/headers';

import { auth } from '@/auth';
import { db } from '@/db';
import { events } from '@/db/schema';
import { CreateEventForm } from '@/components/create-event-form';

export default async function Page() {
  const session = await auth.api.getSession({
    headers: await headers()
  });

  if (!session) {
    redirect('/login');
  }

  const userEvent = await db
    .select()
    .from(events)
    .where(eq(events.userId, session.user.id));

  return (
    <div>
      <CreateEventForm />
      <h2>Events:</h2>
      <pre>{JSON.stringify(userEvent, null, 2)}</pre>
    </div>
  );
}
```

```tsx
'use client';

import { zodResolver } from '@hookform/resolvers/zod';
import { useForm } from 'react-hook-form';
import { z } from 'zod';
import { createEventAction } from '@/server-actions';

const formSchema = z.object({
  name: z.string()
});

type Form = z.infer<typeof formSchema>;

export function CreateEventForm() {
  const form = useForm<Form>({
    resolver: zodResolver(formSchema)
  });

  return (
    <form
      onSubmit={form.handleSubmit(async values => {
        await createEventAction(values);
      })}
    >
      <input {...form.register('name')} />
      <button type="submit">Submit</button>
    </form>
  );
}
```

```tsx
'use server';

import { revalidatePath } from 'next/cache';
import { headers } from 'next/headers';

import { auth } from '@/auth';
import { db } from '@/db';
import { events } from '@/db/schema';

export async function createEventAction(input: { name: string }) {
  const session = await auth.api.getSession({
    headers: await headers()
  });

  if (!session) {
    return {
      message: 'User must be signed in to create an event.'
    };
  }

  await db.insert(events).values({
    name: input.name,
    userId: session.user.id
  });

  revalidatePath('/protected');
}
```

## User signout

If the app offers a login option, the user must also be able to log out. Better Auth exposes `signOut` from the client instance, which deletes the session on the server and clears the client session state. The implementation might look like this.

```tsx
import { redirect } from 'next/navigation';
import { headers } from 'next/headers';

import { auth } from '@/auth';
import { SignoutButton } from '@/components/signout-button';

export default async function Page() {
  const session = await auth.api.getSession({
    headers: await headers()
  });

  if (!session) {
    redirect('/login');
  }

  return (
    <div>
      <SignoutButton />
    </div>
  );
}
```

```tsx
'use client';

import { useRouter } from 'next/navigation';

import { signOut } from '@/auth/client';

export function SignoutButton() {
  const router = useRouter();

  return (
    <button
      onClick={() =>
        signOut({
          fetchOptions: {
            onSuccess: () => router.push('/login')
          }
        })
      }
      type="button"
    >
      Sign out
    </button>
  );
}
```

<MdxComment>
  Note the `onSuccess` callback. `signOut()` only clears the session - it does
  not navigate anywhere and it does not re-render the server component that
  wrapped this button. Without the explicit `router.push`, the page we are
  standing on keeps showing the already rendered content of a logged in user
  until the next navigation, even though the session is gone. `router.refresh()`
  is the alternative when we want to stay on the same route.
</MdxComment>

## Protected pages

Until now, we have ensured that only logged in users access the site by getting the session on each page separately. This can introduce significant code duplication over time. A `proxy.ts` file can perform an **optimistic** check before a request reaches the route: it checks whether a Better Auth session cookie is present and redirects obvious anonymous requests to the login page.

```ts
import { type NextRequest, NextResponse } from 'next/server';
import { getSessionCookie } from 'better-auth/cookies';

const PUBLIC_ROUTES = ['/login'];

export default function proxy(request: NextRequest) {
  const isPublic = PUBLIC_ROUTES.some(route =>
    request.nextUrl.pathname.startsWith(route)
  );

  if (!isPublic && !getSessionCookie(request)) {
    const redirectUrl = new URL('/login', request.url);
    redirectUrl.searchParams.set('callbackUrl', request.nextUrl.href);

    return NextResponse.redirect(redirectUrl);
  }
}

export const config = {
  matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)']
};
```

<MdxComment>
  Since Next.js 16, this file is called `proxy.ts`; the old name was
  `middleware.ts`. This is useful for a quick redirect, but a cookie can be
  expired or forged. Always perform the real authorization close to the data or
  server action as well, by calling `auth.api.getSession`.
</MdxComment>

## Getting session client-side

If we need the session in a client component, Better Auth's React client exposes `useSession`. Unlike the old NextAuth integration, it does **not** require a provider around the whole application.

```tsx
'use client';

import { useSession } from '@/auth/client';

export function UserMenu() {
  const { data: session, isPending } = useSession();

  if (isPending) {
    return <span>Loading...</span>;
  }

  if (!session) {
    return <a href="/login">Sign in</a>;
  }

  return <span>Signed in as {session.user.name}</span>;
}
```

On its first render the hook retrieves the session from Better Auth's endpoint, so `data` is initially `null` and `isPending` is true. Once it has finished, `data` is either the session or `null`. Do not use this as the only protection for data: client-side checks happen after JavaScript has loaded and can be bypassed.

## Metadata

If you want users to find your page through search engines such as Google, it is important to set up its metadata correctly. In the past, when SPAs were the go-to way to implement React apps, this was difficult. With Next.js, we can define static metadata and generate dynamic metadata and previews for dynamic pages.

### Defining metadata

Each `layout.tsx` and `page.tsx` file can export its own metadata, which Next.js merges. You can export metadata in two ways.

```tsx
import type { Metadata } from 'next';

export const metadata: Metadata = {
  title: '...'
};
```

```tsx
import type { Metadata } from 'next';

export async function generateMetadata(
  { params }: PageProps<'/products/[id]'>
): Promise<Metadata> {
  const { id } = await params;

  return {
    title: `Product ${id}`
  };
}
```

<MdxComment>
  `params` is a promise in Next.js 16, so it must be awaited. If you use `fetch`
  or a cached data function in `generateMetadata`, the same caching rules apply
  as in other React Server Components.
</MdxComment>

### Title and description

These are the two most basic attributes. Search engines use them to display your page in search results.

```tsx
// src/app/layout.tsx

export const metadata: Metadata = {
  title: {
    template: '%s | My Site',
    default: 'My Site'
  }
};
```

```tsx
// src/app/about/page.tsx

export const metadata: Metadata = {
  title: 'About'
};

// Result will be 'About | My Site'
```

[Here](https://nextjs.org/docs/app/api-reference/functions/generate-metadata) is a complete list of all the metadata attributes you can use.

### Dynamic image generation

It is possible to generate image previews dynamically from JSX with the `next/og` package. By adding `opengraph-image.tsx`, we can create a dynamic image preview for a page.

```tsx
import { ImageResponse } from 'next/og';

// Image metadata
export const alt = 'About Acme';
export const size = {
  width: 1200,
  height: 630
};

export const contentType = 'image/png';

// Image generation
export default async function Image() {
  // Font
  const interSemiBold = fetch(
    new URL('./Inter-SemiBold.ttf', import.meta.url)
  ).then(res => res.arrayBuffer());

  return new ImageResponse(
    (
      // ImageResponse JSX element
      <div
        style={{
          fontSize: 128,
          background: 'white',
          width: '100%',
          height: '100%',
          display: 'flex',
          alignItems: 'center',
          justifyContent: 'center'
        }}
      >
        About
      </div>
    ),
    {
      // ImageResponse options
      // For convenience, we can re-use the exported opengraph-image
      // size config to also set the ImageResponse's width and height.
      ...size,
      fonts: [
        {
          name: 'Inter',
          data: await interSemiBold,
          style: 'normal',
          weight: 400
        }
      ]
    }
  );
}
```

### Sitemap, robots.txt and icons

These metadata conventions use file-based routing, like `opengraph-image`. `robots.ts` and `sitemap.ts` apply to the whole site, so they belong in the root of the `app` directory.

Example of `src/app/robots.txt`:

```txt
User-Agent: *
Allow: /
Disallow: /private/

Sitemap: https://acme.com/sitemap.xml
```

Example of dynamic `src/app/sitemap.ts`:

```ts
import { MetadataRoute } from 'next';

export default function sitemap(): MetadataRoute.Sitemap {
  return [
    {
      url: 'https://acme.com',
      lastModified: new Date(),
      changeFrequency: 'yearly',
      priority: 1
    },
    {
      url: 'https://acme.com/about',
      lastModified: new Date(),
      changeFrequency: 'monthly',
      priority: 0.8
    },
    {
      url: 'https://acme.com/blog',
      lastModified: new Date(),
      changeFrequency: 'weekly',
      priority: 0.5
    }
  ];
}
```

## Deployment

The easiest way to host a Next.js project is [Vercel](https://vercel.com), since both products come from the same company. Vercel supports all Next.js features and provides cloud services such as Blob storage, Cron Jobs, databases and caches from the Vercel Marketplace, and preview deployments with comments. Its free tier is useful for personal and small projects, subject to its current usage limits.

### Hosting on Vercel

To host your project on Vercel, sign in with your GitHub account and choose the repository to host. Vercel detects the project type and configures the build and deployment steps. New commits to the main branch create production deployments; commits to other branches create preview deployments.

## Turbopack

Turbopack is an incremental bundler optimized for JavaScript and TypeScript, written in Rust by the Next.js team at Vercel.

<MdxComment>Once Turbopack performs a task it never does it again.</MdxComment>

Since Next.js 16, Turbopack is stable and is the default bundler for both `next dev` and `next build`. It uses a unified incremental graph and lazy bundling to reduce compilation work, especially in large applications. If a project relies on a custom Webpack configuration that Turbopack does not support, it can opt out with the `--webpack` flag.

No flag is needed to use Turbopack: run the usual `pnpm dev`. To run Webpack instead, use `next dev --webpack`.

## Turborepo

Turborepo is a tool for creating a monorepo containing several applications and packages. It makes it easier to create applications, share code between them and simplify deployment.

A typical example is creating a custom UI library that needs to be used in multiple applications. At the same time, by changing one of the components in the UI library, we want the changes to be reflected in all applications that use this library (without having to update the library version in all applications separately).

At InQool we use Turborepo for many projects. We have a shared UI library, as well as shared `tsconfig`, ESLint and Tailwind configuration. Therefore, most of our applications use the same settings and developers can switch between projects more easily.
